## 1. Gamma API (gamma-api.polymarket.com): endpoints, query params, response fields, JSON-encoded strings, pagination

### Takeaway
Gamma is the public, no-auth market-metadata API. In late 2026 the official SDK lists markets and events through **cursor ("keyset") endpoints `/markets/keyset` and `/events/keyset`** rather than offset paging, and the market object now carries explicit fee fields (`feesEnabled`, `feeType`, `feeSchedule{rate, exponent, takerOnly, rebateRate}`). `outcomes`, `outcomePrices` and `clobTokenIds` are JSON-encoded strings that must be `json.loads`-ed.

### Inferences
- Example read-only requests a client can build from the above (constructed from the cited parameter names, not executed): `GET https://gamma-api.polymarket.com/markets/keyset?closed=false&order=volumeNum&ascending=false&limit=100` then `...&after_cursor=<next_cursor>`; `GET https://gamma-api.polymarket.com/events/keyset?closed=false&tag_slug=politics&end_date_min=2026-11-18T00:00:00Z&liquidity_min=10000`; `GET https://gamma-api.polymarket.com/markets/slug/<slug>`.
- A robust parser should: (a) `json.loads` `outcomes`/`outcomePrices`/`clobTokenIds` when they arrive as strings and accept lists too; (b) treat numeric-looking strings (`volume`, `liquidity`, `bestBid`, …) as decimals; (c) tolerate missing/`""` values for resolution fields; (d) skip markets whose `outcomes` length ≠ 2 (the official SDK silently drops non-binary rows).
- `description` on the market/event is where the human-readable resolution rules live; `resolutionSource` is the named source. There is no separate "rules" field in the SDK model.
- The offset-style `/markets` and `/events` list endpoints were the documented interface through early 2026 and are what most third-party code still uses; the official SDK's exclusive use of `/keyset` (and its comment about an "upstream offset cap" for comments) suggests deep offset paging is capped or discouraged. Build new code on `/keyset`.
- **[UNVERIFIED-MEMORY]** On the legacy list endpoints the response was a bare JSON array and there was no total count; `tag_id`, `related_tags`, `closed`, `active`, `archived`, `liquidity_num_min`, `volume_num_min`, `end_date_min/max`, `start_date_min/max` were supported filters.

### Gaps
- Could not open the Gamma API reference on docs.polymarket.com (blocked), so the server-side maximum `limit` for `/markets/keyset` and `/events/keyset`, and whether legacy offset endpoints now enforce a hard offset cap, are unconfirmed. SKILLS says `limit` 1–500 for the legacy endpoints.
- `active` is not a parameter of the SDK's `/markets/keyset` builder (only `closed`); whether the keyset endpoint accepts `active` is unconfirmed.
- No live response was captured, so the exact presence/format of `feeSchedule` on every market, and whether fields such as `umaBond`, `umaReward`, `negRiskMarketID` on markets still exist, is unverified.

## 2. CLOB API (clob.polymarket.com): public endpoints, auth (L1/L2), signature types, allowances, order types, sizes/ticks, market orders, batch, heartbeat

### Takeaway
The CLOB moved to **"CLOB V2"** in 2026: a new EIP-712 order struct (domain `Polymarket CTF Exchange`, version `"2"`, fields `timestamp`/`metadata`/`builder` replace `nonce`/`feeRateBps`/`taker`), new exchange contracts, and a new collateral token (pUSD). Read endpoints (`/book`, `/price`, `/midpoint`, `/spread`, `/tick-size`, `/neg-risk`, `/prices-history`, …) are unchanged in shape and need no auth; trading needs L1 (EIP-712) to mint API creds and L2 (HMAC) per request. A dead-man's-switch heartbeat (`POST /v1/heartbeats`) is **opt-in**: once you send one, you must keep sending roughly every 5 s or all your open orders are cancelled.

### Cited Findings
**Base URLs and versions**
- Production: CLOB REST `https://clob.polymarket.com`; market WS `wss://ws-subscriptions-clob.polymarket.com/ws/market`; user WS `wss://ws-subscriptions-clob.polymarket.com/ws/user`; relayer `https://relayer-v2.polymarket.com`; chain id 137 (Polygon). — [PYSDK environments.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/environments.py)
- The Rust client README tabulates three protocols: V1 = CTF token, host `https://clob.polymarket.com`, collateral USDC.e, EIP-712 domain version `"1"`; V2 = CTF token, host `https://clob-v2.polymarket.com`, collateral pUSD, domain version `"2"`; V3 = "Polymarket V2 position", same host, pUSD, domain version `"3"`. The protocol is auto-detected via `GET /version`. "V2 orders add `timestamp`, `metadata`, and `builder` fields. V1 orders use `taker`, `nonce`, and `feeRateBps` instead." — [rs-clob-client-v2 README](https://github.com/Polymarket/rs-clob-client-v2)
- The newer unified Python SDK (Nov 2026) signs V2 orders against **`https://clob.polymarket.com`** with V2 exchange addresses, i.e. the main host now serves V2. — [PYSDK environments.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/environments.py); conflicts with the host column in [rs-clob-client-v2 README](https://github.com/Polymarket/rs-clob-client-v2) (likely written before cut-over).

**Authentication**
- L1 (create/derive API key): EIP-712 typed data, domain `{name: "ClobAuthDomain", version: "1", chainId}`, primary type `ClobAuth{address, timestamp (string), nonce (uint256), message}` with message `"This message attests that I control the given wallet"`. Headers: `POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`, `POLY_NONCE`. Endpoints: `POST /auth/api-key` (create), `GET /auth/derive-api-key` (derive); the SDK tries create and falls back to derive on HTTP 400. — [PYSDK l1_auth.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/l1_auth.py), [PYSDK actions/auth.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/auth.py)
- L2 (every trading request): HMAC-SHA256 over the string `f"{timestamp}{method}{path}{body}"` using the url-safe-base64-decoded `secret`; signature is url-safe base64. Five headers required: `POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`, `POLY_API_KEY`, `POLY_PASSPHRASE`. — [PYSDK hmac.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/hmac.py), [SKILLS authentication.md](https://github.com/Polymarket/agent-skills/blob/main/authentication.md)
- Other auth endpoints: `GET /auth/api-keys`, `DELETE /auth/api-key`, `GET /auth/ban-status/closed-only`, read-only keys `POST /auth/readonly-api-key` / `GET /auth/readonly-api-keys`, builder keys `/auth/builder-api-key`. — [PCC2 endpoints.py](https://github.com/Polymarket/py-clob-client-v2/blob/main/py_clob_client_v2/endpoints.py)
- Signature types: `0` = EOA, `1` = POLY_PROXY (Magic/email proxy wallet), `2` = GNOSIS_SAFE (browser-wallet Safe; "most common"), `3` = DEPOSIT_WALLET / `POLY_1271` (EIP-1271 smart-contract wallet, new in V2). — [PYSDK wallet.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/wallet.py), [EXV2 README](https://github.com/Polymarket/ctf-exchange-v2), [SKILLS SKILL.md](https://github.com/Polymarket/agent-skills/blob/main/SKILL.md)
- Funder: "the actual address that holds your funds"; for proxy/Safe wallets the signing key differs from the funder, and the Rust SDK derives the funder deterministically via CREATE2 from the signer EOA. For EOA (type 0) the funder is the EOA itself and it needs POL for gas. — [rs-clob-client-v2 README](https://github.com/Polymarket/rs-clob-client-v2), [SKILLS SKILL.md](https://github.com/Polymarket/agent-skills/blob/main/SKILL.md)

**Allowances**
- "MetaMask and EOA users must set token allowances. If you are using a proxy or Safe-type wallet, then you do not." Two approvals: the collateral ERC-20 and the conditional tokens (ERC-1155), each for the exchange contracts. — [rs-clob-client-v2 README](https://github.com/Polymarket/rs-clob-client-v2)
- CLI: "Polymarket contracts need ERC-20 (pUSD) and ERC-1155 (CTF token) approvals"; `polymarket approve check` (read-only), `polymarket approve set` ("sends on-chain transactions, needs MATIC for gas"). — [CLI README](https://github.com/Polymarket/polymarket-cli)
- Approval matrix (pre-V2 wording): buy → approve collateral to the (standard or neg-risk) Exchange; sell → approve conditional tokens to that Exchange; split → approve collateral to CTF; neg-risk conversion → approve conditional tokens to the Neg Risk Adapter. — [SKILLS ctf-operations.md](https://github.com/Polymarket/agent-skills/blob/main/ctf-operations.md)
- Balance/allowance endpoints: `GET /balance-allowance`, `GET /balance-allowance/update` (L2). — [PCC2 endpoints.py](https://github.com/Polymarket/py-clob-client-v2/blob/main/py_clob_client_v2/endpoints.py)

**Order struct, placement and types**

- Batch: `POST /orders`, maximum **15** orders per request. — [PYSDK orders/post.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/orders/post.py), [SKILLS order-patterns.md](https://github.com/Polymarket/agent-skills/blob/main/order-patterns.md)

**Heartbeat**
- `POST /v1/heartbeats` with body `{"heartbeat_id": ""}` on the first call, then the `heartbeat_id` returned by the previous response. On mismatch the server returns HTTP 400 `{"error_msg": "Invalid Heartbeat ID", "heartbeat_id": "<expected>"}`. — [PYSDK order_heartbeats.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/order_heartbeats.py), [PYSDK models/clob/order_heartbeats.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/clob/order_heartbeats.py)
- Semantics: "The first accepted send enables timeout cancellation for ALL open orders owned by this API key, across markets and processes. Only start when you can keep sending every five seconds. After ten seconds without an accepted send, the server attempts cancel-all; timing and success are not guaranteed… There is no disarm operation." — [PYSDK clients/secure.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/clients/secure.py)
- Older wording: "If a valid heartbeat is not received within 10 seconds (with up to a 5-second buffer), all of your open orders will be cancelled." — [SKILLS order-patterns.md](https://github.com/Polymarket/agent-skills/blob/main/order-patterns.md)

### Inferences
- The heartbeat is opt-in (armed by the first accepted send). A small bot that places a few resting orders does not have to use it; if it does, it needs a dedicated 5-second loop and must cancel orders explicitly on shutdown.
- `expiration` is transmitted in the POST body but is **not** part of the V2 signed struct shown above, so GTD expiry is enforced by the operator/matching engine rather than by the on-chain signature (V1 had `expiration` in the signed order). This is read from code, not stated in docs.
- For a paper-trading simulator: quantise prices to the current `tick_size`, reject sizes below `min_order_size`, model marketable orders as walking `asks`/`bids` from `/book`, apply the `takerDelayMs` delay on sports markets, and reject post-only orders that cross.
- Amount encoding follows the long-standing convention (BUY: `makerAmount` = collateral paid, `takerAmount` = shares received; SELL: reversed; both ×10^6), consistent with `parse_amount` using 6 decimals.
- **[UNVERIFIED-MEMORY]** Typical minimum sizes before 2026 were 5 shares for a resting limit order and about $1 notional for marketable orders; read `min_order_size` per market rather than hard-coding.
- **[UNVERIFIED-MEMORY]** L2 `POLY_TIMESTAMP` is UNIX seconds and the signed `path` excludes the query string.

### Gaps
- Could not read the docs' CLOB V2 migration page, so the official cut-over date and exact deprecation timeline for V1 signing are unconfirmed here. **[UNVERIFIED-MEMORY]** My recollection is that V2 went live on 28 April 2026 with all open V1 orders cancelled.
- `GET /fee-rate` returning `base_fee` is a legacy V1-style field; whether it is still meaningful under V2 (where fees come from `fd` on `/clob-markets/{id}`) is unconfirmed.
- Did not verify whether `/sampling-markets` still reflects reward-eligible markets or what its response fields are.
- Whether read-only API keys (`/auth/readonly-api-key`) are generally available is unknown.

## 4. Data API (data-api.polymarket.com): positions, trades, activity, holders, leaderboard

## 5. WebSocket channels (market, user) and RTDS

### Takeaway
Two CLOB WebSocket channels exist: a public **market** channel keyed by token IDs and an authenticated **user** channel keyed by condition IDs, both needing an application-level text `PING` every 10 s. A separate real-time data service (RTDS) streams activity/comments/crypto prices, and in 2026 Polymarket added a newer authenticated price-stream service ("PolyBolt") with legacy RTDS price topics marked deprecated.

### Cited Findings
- Endpoints: `wss://ws-subscriptions-clob.polymarket.com/ws/market` (no auth), `wss://ws-subscriptions-clob.polymarket.com/ws/user` (API creds in the subscribe message), sports `wss://sports-api.polymarket.com/ws`, RTDS `wss://ws-live-data.polymarket.com`, and a newer realtime endpoint `wss://ws-live-v2.polymarket.com/ws`. — [PYSDK environments.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/environments.py)

## 7. Negative-risk markets (neg risk adapter)

### Takeaway
A "neg risk" event is a set of mutually exclusive binary markets (exactly one resolves Yes) wired through the NegRiskAdapter so that a No share in one outcome can be converted into Yes shares in every other outcome. This ties the outcome prices together (the Yes prices should sum to about 1) and means neg-risk markets trade on a separate exchange contract that orders must be signed against.

### Cited Findings
- "The contracts… unify mutually exclusive binary markets into a single multi-outcome market structure… a set of binary YES/NO markets of which one and only one will resolve true." — [neg-risk-ctf-adapter README](https://github.com/Polymarket/neg-risk-ctf-adapter)
- Worked equivalence: with candidates A, B, C, holding 1 NO-A + 1 NO-B "is equivalent to 1 USDC and 1 YES C… The NegRiskAdapter is designed precisely to allow a position of 1 or more NO tokens to be converted to the equivalent position of YES tokens plus some amount of USDC." — [neg-risk-ctf-adapter README](https://github.com/Polymarket/neg-risk-ctf-adapter)
- Mechanism: collateral is wrapped into "WrappedCollateral, which is then used to collateralize all underlying markets", letting the adapter release USDC during conversion. A Vault "holds USDC and Yes tokens which are collected as fees from users who choose to convert NO positions, given a positive fee rate." — [neg-risk-ctf-adapter README](https://github.com/Polymarket/neg-risk-ctf-adapter)
- Resolution constraints: "once one question is resolved as Yes/True, all other questions must be resolved as No/False… it should not be the case that all questions for a given market resolve to No/False"; the UMA adapter's `[1,1]` (50/50) outcome "is not a valid outcome for the NegRiskAdapter." — [neg-risk-ctf-adapter README](https://github.com/Polymarket/neg-risk-ctf-adapter)
- Simplified conversion rule: "A No token in any market can be converted into 1 Yes token in every other market. Conversion is atomic through the Neg Risk Adapter contract." — [SKILLS ctf-operations.md](https://github.com/Polymarket/agent-skills/blob/main/ctf-operations.md)
- Identification in the API: `negRisk: true` on the event or market; `GET /neg-risk?token_id=` → `{"neg_risk": bool}`; `nr` on `/clob-markets/{id}`; `neg_risk` on `/book`. Events also expose `negRiskMarketID`, `negRiskFeeBips`, `enableNegRisk`, `negRiskAugmented`. — [SKILLS ctf-operations.md](https://github.com/Polymarket/agent-skills/blob/main/ctf-operations.md), [PYSDK orders/market_data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/orders/market_data.py), [PYSDK models/gamma/event.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/gamma/event.py)
- Separate contracts (V2, Polygon): standard exchange `0xE111180000d2663C0091e4f400237545B87B996B`, neg-risk exchange `0xe2222d279d744050d28e00520010520000310F59`, neg-risk adapter `0xd91E80cF2E7be2e162c6513ceD06f1dD0dA35296`. The order's EIP-712 `verifyingContract` must be the right one for the market. — [PYSDK environments.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/environments.py), [EXV2 README](https://github.com/Polymarket/ctf-exchange-v2)
- Augmented neg risk (`negRiskAugmented: true`): events with named outcomes, placeholder outcomes and an explicit "Other". "Only trade on named outcomes — ignore placeholders… 'Other' definition changes as placeholders are clarified — avoid trading it directly." — [SKILLS ctf-operations.md](https://github.com/Polymarket/agent-skills/blob/main/ctf-operations.md)
- Data API position rows flag `negative_risk`, resolutions carry `market_type` of `BINARY`, `INCREMENTAL_NEGRISK` or `ATOMIC_NEGRISK`, and `CONVERSION` is an activity type. — [PYSDK models/data/portfolio.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/portfolio.py), [PYSDK models/data/common.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/common.py)

### Inferences
- Pricing implication: in an n-outcome neg-risk event, buying No on outcome i at price q_i is equivalent to buying Yes on all other outcomes for a net cost; if the sum of best Yes asks is below 1 (or the sum of Yes bids above 1) there is a theoretical arbitrage via buy-all-Yes / convert. In practice it is bounded by fees, spread, depth and any `negRiskFeeBips`. A simulator should compute `sum(yes_mid)` across an event's markets as a consistency check and treat large deviations as a data or liquidity signal, not free money.
- For augmented events the Yes prices of *named* outcomes legitimately sum to less than 1 because of the "Other"/placeholder mass; do not flag that as mispricing.
- A read-only/paper bot never needs to call the adapter; it only needs the `negRisk` flag to (a) group markets by event and (b) know which exchange a real order would be signed for.

### Gaps
- The current value of the conversion fee (`negRiskFeeBips`) on live events was not observed.
- How conversion interacts with the new pUSD collateral adapters (`NegRiskCtfCollateralAdapter`) was not read in detail.

## 8. Fees as exposed by the API, taker-fee formula, maker rebates and liquidity rewards

### Takeaway
Under CLOB V2 fees are not embedded in the signed order; they are set per market and applied at match time. The API exposes them as a `(rate, exponent)` pair, and both official SDKs compute the taker fee as **`fee_usdc = shares × rate × (p × (1 − p))^exponent`** — zero at the extremes, largest at p = 0.5. Gamma additionally exposes `feesEnabled`, `feeType`, `takerOnly` and a maker `rebateRate`. Liquidity-reward eligibility is exposed per market via `rewardsMinSize` and `rewardsMaxSpread`.

### Cited Findings
- Formula in the unified SDK: `effective_rate = fee.rate * ((price * (1 - price)) ** fee.exponent)`; `platform_fee = (amount / price) * effective_rate` where `amount` is USDC spent on a BUY (so `amount / price` is shares); an optional `builder_fee = amount * builder_taker_fee_rate` is added. — [PYSDK orders/market.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/orders/market.py)
- Same formula in the V2 CLOB client: `platform_fee_rate = fee_rate * (price * (1 - price)) ** fee_exponent`; `platform_fee = (fee_base_amount / price) * effective_platform_fee_rate`. — [PCC2 fees.py](https://github.com/Polymarket/py-clob-client-v2/blob/main/py_clob_client_v2/fees.py)
- Where the parameters come from: `GET /clob-markets/{condition_id}` → `fd: {"r": rate, "e": exponent}` (missing `fd` ⇒ rate 0). Gamma market: `feesEnabled`, `feeType`, `feeSchedule: {rate, exponent, takerOnly, rebateRate}`. — [PYSDK orders/market_data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/orders/market_data.py), [PYSDK models/gamma/market.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/gamma/market.py)
- Legacy field: `GET /fee-rate?token_id=` → `base_fee` (the V1 `fee_rate_bps`), and the WS `last_trade_price` event carries `fee_rate_bps`. V1 orders embedded `feeRateBps`; V2 orders do not. — [PCC2 client.py](https://github.com/Polymarket/py-clob-client-v2/blob/main/py_clob_client_v2/client.py), [SKILLS websocket.md](https://github.com/Polymarket/agent-skills/blob/main/websocket.md), [rs-clob-client-v2 README](https://github.com/Polymarket/rs-clob-client-v2)
- On-chain cap: the V2 exchange has a "configurable max fee rate — admin-settable maximum fee rate in basis points (default 500 = 5%), enforced per-order", and emits a `FeeCharged` event. — [EXV2 README](https://github.com/Polymarket/ctf-exchange-v2)
- Builder fees: a per-builder taker fee rate is fetched from `GET /fees/builder-fees/{builder_code}` and applies when an order carries a non-zero `builder` code. — [PYSDK orders/market_data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/orders/market_data.py)
- Rebates: endpoint `GET /rebates/current` (by `date` and `maker_address`) returns current maker rebates; activity types include `MAKER_REBATE` and `TAKER_REBATE`; the SDK changelog mentions "taker-tier upgrade notifications". — [PYSDK actions/rewards.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/rewards.py), [PYSDK models/data/common.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/common.py), [PYSDK CHANGELOG](https://github.com/Polymarket/py-sdk/blob/main/CHANGELOG.md)
- Liquidity rewards API: `GET /rewards/markets/current`, `GET /rewards/markets/{condition_id}`, `GET /rewards/markets/multi`, `GET /rewards/user`, `/rewards/user/total`, `/rewards/user/percentages`, `/rewards/user/markets`, plus `GET /order-scoring` / `POST /orders-scoring` to test whether specific orders are scoring. — [PYSDK actions/rewards.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/rewards.py)
- Reward parameters per market: `rewards_max_spread`, `rewards_min_size`, `rewards_config[]` with `asset_address`, `start_date`, `end_date`, `rate_per_day`, `total_rewards`; also `native_daily_rate`, `sponsored_daily_rate`, `sponsors_count`, `total_daily_rate`, `market_competitiveness`. Gamma mirrors `rewardsMinSize`, `rewardsMaxSpread`, `clobRewards[].rewardsDailyRate`, `holdingRewardsEnabled`. — [PYSDK models/clob/rewards.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/clob/rewards.py), [PYSDK models/gamma/market.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/gamma/market.py)
- Bridge: "Withdrawals are instant and free — Polymarket does not charge withdrawal fees"; deposit minimums are $7 from Ethereum and $2 from most other chains. — [SKILLS bridge.md](https://github.com/Polymarket/agent-skills/blob/main/bridge.md)

### Inferences
- Simulator fee model: `fee = shares * rate * (p*(1-p))**exponent`, charged to the taker only when `takerOnly` is true; makers pay nothing and may earn `rebateRate` × fees. Worked example with a hypothetical `rate = 0.05`, `exponent = 1`: 100 shares at p = 0.50 → 100 × 0.05 × 0.25 = $1.25; at p = 0.90 → 100 × 0.05 × 0.09 = $0.45. Always read `rate`/`exponent` per market rather than assuming a category value.
- Because the SDK formula computes the fee on a BUY in collateral on top of the spend, a market BUY that spends the whole balance must be shrunk: `amount = max_spend / (1 + effective_rate/price + builder_rate)` (this is exactly what the SDK does).
- **[UNVERIFIED-MEMORY]** Fee history as I recall it: no trading fees on most markets through 2025; taker fees with maker rebates introduced on 15-minute crypto markets in January 2026; extended to more categories in February–March 2026; and a category schedule effective around 30 March 2026 with rates roughly: crypto 0.072, sports 0.03, finance/politics/tech/mentions 0.04, economics/culture/weather/other 0.05, geopolitics 0, all with exponent 1 and maker rebates of roughly 20–25% of fees. These values may have changed since; the per-market `feeSchedule`/`fd` is authoritative.
- **[UNVERIFIED-MEMORY]** Liquidity-rewards scoring: orders within `rewardsMaxSpread` (in cents) of the size-adjusted midpoint and at least `rewardsMinSize` shares score quadratically, S = ((v − s)/v)² × size, sampled every minute, with a two-sided requirement when the midpoint is below 0.10 or above 0.90 and a single-sided penalty factor (c ≈ 3) otherwise; paid daily around midnight UTC with a small minimum payout.

### Gaps
- The current official fee table by category, the exact definition of `feeType` values, and the current maker-rebate percentages were **not verified** (docs blocked).
- Whether fees on SELL orders are taken in collateral from proceeds, and rounding rules for the fee, were not confirmed in docs (the SDK code only shows BUY-side adjustment).
- Whether "holding rewards" (`holdingRewardsEnabled`, `YIELD` activity type) pay interest on positions, and at what rate, was not determined.

## 9. Resolution: UMA Optimistic Oracle flow, redemption, post-resolution book, 2025-2026 changes

### Takeaway
Legacy (v1/CTF) markets resolve through the UMA CTF Adapter: a proposal with about a 2-hour liveness, an automatic reset on the first dispute, and escalation to UMA's DVM (48–72 h) on a second dispute. By late 2026 the data model shows three reporter families — **UMA optimistic oracle, Chainlink, and EOA** — plus "managed proposal" timing and a separate v2-protocol resolution status, so UMA is no longer the only resolution path. Winning shares redeem for 1.00 of collateral with no deadline.

### Cited Findings
- Initialisation: when a market is deployed, its parameters (ancillary data, request timestamp, reward token, reward) are stored on-chain, the condition is prepared on the CTF, and a request is sent to the Optimistic Oracle. — [uma-ctf-adapter README](https://github.com/Polymarket/uma-ctf-adapter)
- "UMA Proposers will then respond to the request… If the resolution data is not disputed, the data will be available to the Adapter after a defined liveness period (currently about 2 hours)." — [uma-ctf-adapter README](https://github.com/Polymarket/uma-ctf-adapter)
- "The first time a request is disputed, the market is automatically `reset`, meaning, a new Optimistic Oracle request is sent out… If the request is disputed again… the Optimistic Oracle falls back to UMA's DVM… The DVM will return data after a 48 - 72 hour period." Afterwards "anyone can call `resolve`". — [uma-ctf-adapter README](https://github.com/Polymarket/uma-ctf-adapter)
- Resolution lifecycle statuses exposed by the Data API: `initialized`, `posed`, `proposed`, `challenged`, `reproposed`, `disputed`, `active`, `arbitration`, `resolved`. — [PYSDK models/data/common.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/common.py)
- `GET /v2/resolutions` (by `question_id`, `condition_id` or up to 20 `event_id`s) returns: `status`, `extended_review`, `expected_settlement_time` ("Earliest estimated settlement time, not a deadline; may have elapsed"), `settlement_time_basis`, `was_disputed`, `new_version_q` (question rules updated), `proposed_price`, `reproposed_price`, `price`, `transaction_hash`, `last_update_timestamp`, `market_type`, `payouts` (pair, 1e6-scaled), `resolution_source` (`reported`|`derived`), `reporter`, `was_arbitrated`, `resolved_block`, `resolved_at`. — [PYSDK models/data/resolutions.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/resolutions.py), [PYSDK actions/data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/data.py)
- Reporter families: `UMA_OO`, `CHAINLINK`, `EOA`. Settlement-time bases: `managed_proposal_expiration`, `proposal_expiration`, `liveness`, `dvm_round_estimate` ("Voting estimates can roll to a later round"). — [PYSDK models/data/common.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/common.py)
- Gamma fields: `umaResolutionStatus` (`requested`, `proposed`, `disputed`, `resolved`, `settled`), `resolutionSource`, `resolvedBy`, `questionID`, `negRiskRequestID`; for v2-protocol markets `resolutionStatus` (`inactive`|`active`|`resolved`), `requestId` ("Oracle request ID: a condition ID or the parent event ID"), `onchainEventId`. Events carry `automaticallyResolved`. — [PYSDK models/gamma/market.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/gamma/market.py), [PYSDK models/gamma/event.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/gamma/event.py)
- Redemption: `redeemPositions(collateralToken, parentCollectionId=0x0, conditionId, indexSets=[1,2])`; "Redemption burns your entire token balance for the condition — no amount parameter. No deadline — winning tokens are always redeemable." Payout vectors `[1,0]` (Yes) / `[0,1]` (No). — [SKILLS ctf-operations.md](https://github.com/Polymarket/agent-skills/blob/main/ctf-operations.md)
- Tooling: `polymarket ctf redeem --condition 0x…`, `polymarket ctf redeem-neg-risk --condition 0x… --amounts "10,5"`; SDK `redeem_positions(...)`; the production environment includes an `auto_redeem_operator` contract (`0xa1200000d0002264C9a1698e001292D00E1b00af`) and the changelog notes "Automatic redemption remains REDEEM". — [CLI README](https://github.com/Polymarket/polymarket-cli), [PYSDK environments.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/environments.py), [PYSDK CHANGELOG](https://github.com/Polymarket/py-sdk/blob/main/CHANGELOG.md)
- Positions API marks resolved holdings with `redeemable: true` and status `REDEEMABLE` / `REDEEMABLE_LOST`. — [PYSDK models/data/portfolio.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/portfolio.py), [PYSDK models/data/common.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/common.py)
- WS signal: the market channel emits `market_resolved` with `winning_asset_id` and `winning_outcome` (needs `custom_feature_enabled`). — [SKILLS websocket.md](https://github.com/Polymarket/agent-skills/blob/main/websocket.md)

### Inferences
- Timeline for capital lock-up in a simulator: undisputed ≈ event end + proposal delay + ~2 h liveness; one dispute adds a fresh proposal + liveness cycle; a second dispute adds a multi-day DVM vote. `expected_settlement_time` from `/v2/resolutions` can replace hard-coded assumptions.
- Once a market is `closed` and no longer `acceptingOrders`, the CLOB book is gone (the TS client's example error for a missing book is "No orderbook exists for the requested token id", HTTP 404, per the [clob-client-v2 README](https://github.com/Polymarket/clob-client-v2)); a bot should treat a 404 on `/book` for a previously live token as "closed/resolved", check Gamma `closed`/`umaResolutionStatus`, and stop quoting. That resolved-market behaviour is inferred, not quoted from docs.
- The presence of `CHAINLINK` and `EOA` reporters, `managed_proposal_expiration` and `automaticallyResolved` strongly suggests: short-dated price markets settle from Chainlink data rather than a UMA proposal, some markets are resolved directly by an authorised account, and UMA proposals now run through a managed (whitelisted-proposer) process.
- **[UNVERIFIED-MEMORY]** Supporting history: UMA governance adopted a "Managed Optimistic Oracle V2" (MOOV2) for Polymarket around August 2025 that restricted who may propose resolutions to an allow-list; Polymarket announced a Chainlink integration around September 2025 for automated resolution of price-based markets; the UMA proposer bond/reward for Polymarket requests was typically a few hundred dollars (≈$750 bond) in USDC.e.

### Gaps
- Could not read docs or UMA governance pages to confirm the MOOV2 date, the allow-list size, current bond amounts, or exactly which market types use Chainlink vs. EOA resolution.
- What "v2 protocol" markets use as an oracle (the `protocol_v2_router`, `binary_module`, `neg_risk_module`, `combinatorial_module`, `position_manager` contracts in the SDK) is not described in any source I could read; whether it is a wholesale move away from UMA is unknown.
- Whether redemption is now automatic for all wallet types (via `auto_redeem_operator`) or only for Polymarket-hosted wallets is unconfirmed.
- The docs' statement of what happens to open orders at resolution was not retrieved.

## 10. Collateral and settlement: USDC.e vs native USDC, 2026 migration, gasless relayer, bridge deposits

### Takeaway
**The collateral token changed in 2026.** Trading on CLOB V2 is denominated in a new ERC-20 — called **pUSD** in the SDK/CLI and "PMCT (PolyMarket Collateral Token)" in the contract repo — at `0xC011a7E12a19f7B1f670d46F03B03f3342E82DFB`, a wrapper around USDC/USDC.e with on/off-ramp contracts. V1 used USDC.e (`0x2791…4174`) directly. Exchange contracts were also replaced.

- For a paper-trading simulator none of this matters beyond units: treat cash as a 6-decimal USD stablecoin and shares as 6-decimal units paying 1.00 on a win.
- **[UNVERIFIED-MEMORY]** pUSD was described at launch as backed 1:1 by USDC, and the V2 exchange + pUSD cut-over happened on or about 28 April 2026 with roughly an hour of downtime and all resting orders wiped.

### Gaps

- Whether the relayer's gasless path is available to individual (non-builder) API users in late 2026 is unconfirmed.

## 12. Historical data for backtesting: prices-history depth/granularity, resolved markets, third-party datasets

### Takeaway
Two official price-history sources exist: the legacy CLOB `GET /prices-history` (`market`, `interval` or `startTs`/`endTs`, `fidelity` in minutes → `[{t,p}]`) and the newer Data API `GET /v2/prices-history` (cursor-paged, `bucket_seconds` granularity, 15-day maximum explicit window, up to 10,000 points per page). Both return a single price series per token — **not** historical order books, spreads or depth — so realistic fill simulation needs either self-recorded book snapshots or a third-party dataset.

### Cited Findings
- CLOB: `GET https://clob.polymarket.com/prices-history` with `market` = token id, plus either `interval` or both `startTs` and `endTs`, optional `fidelity`. Intervals `1h`, `6h`, `1d`, `1w`, `1m`, `max`; "`fidelity: 60` — data points every 60 minutes"; entries `{ t: timestamp, p: price }`; `startTs`/`endTs` are "mutually exclusive with `interval`". — [PCC2 client.py](https://github.com/Polymarket/py-clob-client-v2/blob/main/py_clob_client_v2/client.py), [SKILLS market-data.md](https://github.com/Polymarket/agent-skills/blob/main/market-data.md)
- Data API: `GET https://data-api.polymarket.com/v2/prices-history` with `token_id` and exactly one of `interval` (`max`, `all`, `1m`, `1w`, `1d`, `6h`, `1h`), `start` (+ optional `end`, exclusive) or `as_of`; optional `bucket_seconds`; cursor param `cursor`; max page size 10,000. — [PYSDK actions/data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/data.py)
- Limits enforced by the SDK: explicit `start`/`end` "windows span at most 15 days"; `bucket_seconds` must be ≤ 86,400 and ≥ 600 for `max`/`all`/`1m`, ≥ 300 for `1w`, ≥ 60 otherwise; `as_of` forbids `bucket_seconds` and page size. — [PYSDK actions/data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/data.py), [PYSDK clients/public.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/clients/public.py)
- Point shape: `timestamp` (epoch seconds), `price` ("USDC per share"), `resolution_seconds` ("resolution 0 denotes an exact tick"); results are oldest-first. — [PYSDK models/data/analytics.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/models/data/analytics.py)
- Trade-level history: `GET /v2/trades` (by `condition_id`/`event_id`/`user`, `start`/`end`, 1,000 rows per page) gives individual fills with `price`, `size`, `side`, `timestamp`, `transaction_hash`. — [PYSDK actions/data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/data.py)
- Resolved outcomes for labelling: `GET /v2/resolutions` (`payouts`, `resolved_at`), Gamma `closed=true` markets with final `outcomePrices`, and `GET /v2/tokens` for "outcome asset reference and settlement metadata". — [PYSDK actions/data.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/data.py), [PYSDK clients/public.py](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/clients/public.py)
- On-chain source: Goldsky-hosted subgraphs for Positions, Orders (order book and trade events), Activity (splits/merges/redemptions), Open Interest and PNL, e.g. `https://api.goldsky.com/api/public/project_cl6mb8i9h0003e201j6li0diw/subgraphs/orderbook-subgraph/0.0.1/gn`. — [SKILLS market-data.md](https://github.com/Polymarket/agent-skills/blob/main/market-data.md)
- The unified SDK has optional dataframe extras (`pandas`, `polars`, `arrow`) for pulling these into analysis tools. — [PYSDK pyproject.toml](https://github.com/Polymarket/py-sdk/blob/main/pyproject.toml)

### Inferences
- Finest officially available granularity: 60-second buckets for short lookbacks (`1h`/`6h`/`1d`), 5-minute for a week, 10-minute for a month or the full life of a market — or raw fills from `/v2/trades`. To backtest a market's whole life at 1-minute resolution, walk 15-day `start`/`end` windows with `bucket_seconds=60` (permitted by the SDK validation for explicit windows) or rebuild bars from trades.
- The price series is a single mid/last-style number, so a backtest built only on it will overstate achievable fills. Mitigations: assume a spread (use Gamma's current `spread` as a floor), apply the fee formula from section 8, cap size by observed trade volume, and start recording `/books` snapshots now to build a proprietary depth history.
- Survivorship/look-ahead traps: Gamma's `outcomePrices` on a closed market are the final 0/1 values; `volume`, `liquidity` and `description` are current values, not as-of values; and markets' rules can be amended (`new_version_q`). Use `as_of` queries and resolution timestamps to avoid leakage.
- **[UNVERIFIED-MEMORY]** Known gotcha on the legacy CLOB endpoint: for old/resolved markets, fine `fidelity` values often returned empty or sparse arrays and a coarse fidelity (about 720 minutes) was needed to get data back; and `interval=max` was not always reliable for closed markets.
- **[UNVERIFIED-MEMORY] Third-party dataset leads (names recalled, URLs and current status not checked this session):** Dune Analytics' Polymarket tables/dashboards (on-chain trades since 2020); the open-source `warproxxx/poly_data` pipeline (Gamma markets + Goldsky order-filled events); Jon Becker's `prediction-market-analysis` dataset (tens of GB of Polymarket and Kalshi trades); several Kaggle and Hugging Face dumps of Polymarket markets/trades; commercial vendors offering historical order-book depth such as PolymarketData, Dome and Tardis-style providers. Treat each as unverified until checked.

### Gaps
- Could not test either endpoint, so actual retention depth (how far back minute data really goes), behaviour for resolved markets on `/v2/prices-history`, and whether the legacy CLOB `/prices-history` is scheduled for deprecation are unconfirmed.
- No official historical **order book** archive was found in any source read.
- Third-party dataset URLs, licences, coverage dates and whether they survived the April 2026 contract/collateral migration (new exchange addresses change which on-chain events must be indexed) were not verified.

## 13. Official testnet, sandbox or paper-trading mode

### Takeaway

### Inferences
- Because the official SDK ships no non-production environment and its integration tests use real funds, a public, supported sandbox with realistic liquidity almost certainly does not exist; any Amoy CLOB would have empty books and be useless for strategy evaluation anyway.
- Recommended paper-trading design from the facts above: read Gamma + `/books` in production; simulate fills by walking the live book (FOK/FAK), queue resting orders and fill them only when the opposite side trades through the price; enforce `tick_size`, `min_order_size`, post-only crossing rules and `takerDelayMs`; apply `fee = shares × rate × (p(1−p))^exponent`; mark positions to the bid, not the mid; settle at 1/0 from `/v2/resolutions` or Gamma once `closed`. Keep the signing key absent from the process entirely in paper mode so no code path can place a real order.
- The safest "smallest real step" after paper mode is a read-only API key or L2 creds used only for `GET /data/orders`-style reads, then tiny post-only GTC orders without the heartbeat armed.

### Gaps
